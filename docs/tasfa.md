# TASFA transfer protocol

TASFA is fly.board's chunked, resumable, integrity-checked transfer pipeline
for file uploads and downloads. This document describes the wire protocol, the
session lifecycle, the encryption layout, the browser client, and the service
worker contract. Compression policy details live in
[tasfa-compression.md](tasfa-compression.md); this file covers everything else.

## What TASFA is, and what it is not

TASFA is a **transport and reliability protocol**: chunking, forward error
correction, adaptive parallelism, resume across disconnects, progressive
streaming through a service worker, and per-chunk integrity.

TASFA is **not** an end-to-end or zero-knowledge encryption scheme. Session
keys are generated by the server and delivered to the client inside the
handshake response, which itself travels over TLS. The server stores files in
plaintext (it must, to generate thumbnails and previews), so anyone with server
access or the ability to read the TLS channel already has both the content and
the keys. The per-chunk AES-256-GCM layer buys:

- chunk-level integrity and tamper detection for FEC/recovery traffic,
- an extra integrity floor on top of TLS record verification,
- opaque per-chunk payloads to anything that sees HTTP bodies but not the
  handshake (for example a misbehaving intermediate cache).

Do not describe TASFA to users as "encryption for privacy against the server".
It is a fast/resilient streaming protocol with an integrity layer.

## Architecture

- **Server**: C handlers under `src/handlers/tasfa/`, session state persisted
  on disk under `data/tasfa/uploads/` and `data/tasfa/downloads/`.
- **Browser client**: `public/js/tasfa-download.js` (downloads, media
  upgrades) and the upload portion of `public/js/editor.js`.
- **Service worker**: `public/sw.js` (session-token injection for direct
  streams, progressive stream plumbing, media cache).
- **Optional WASM crypto backend**: `wasm/tasfa_crypto_module.c` run under
  wasmtime when `TASFA_CRYPTO_WASM` is set; `wasm/tasfa_crypto_ref.c` is the
  native reference; `wasm/test_parity.py` verifies byte-identical behavior.
  The browser never uses the WASM module; it uses WebCrypto.

## Endpoint reference

### Download

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/file/download/:id/handshake` | none | create a download session |
| GET | `/file/download/:id/chunk/:n` | `session_id` + `session_token` | fetch chunk `n` (or a span) |
| POST | `/file/download/complete` | session token | close session, bump counter |
| GET | `/file/preview/:id/handshake` | none | session for the preview variant |
| GET | `/file/preview/:id/chunk/:n` | session token | preview chunks |
| GET | `/assets/tasfa/:scope/:filename/handshake` | none | session for a static asset |
| GET | `/assets/tasfa/:scope/:filename/chunk/:n` | session token | asset chunks |

`:scope` is one of `img`, `uploads`, `profile`; `profile` only serves files
registered as profile pictures. Direct `GET /file/download/:id` returns 403
when `use_tasfa=true` unless the request carries valid session headers
(`X-TASFA-Session-ID`, `X-TASFA-Session-Token`) or `?tasfa_fallback=1`.

#### Handshake

Query parameters: `w`/`h` (image thumbnail request, clamped 256-1920 and
rounded to 128 buckets), `preview=1` (video: transcode to a 1080p mp4 preview,
generated on demand), `chunk_size` (client hint), and link telemetry:
`link_stability_score`, `link_effective_type`, `link_downlink_mbps`,
`link_rtt_ms`, `link_retry_events`, `link_timeout_events`, `link_save_data`.

Success 200 JSON:

- `session_id` (32 hex), `session_token` (48 hex)
- `filename`, `mime_type`, `total_size`, `file_id`
- `chunk_size`, `chunk_count` (data chunks only for downloads)
- `initial_parallel_chunks`, `max_parallel_chunks`, `coalesce_chunks`,
  `dispatch_pacing_ms`
- `supports_progressive_streaming`: `true`
- `stream_mode`: `"aes-256-gcm"`, `stream_key_hex` (64 hex),
  `stream_iv_seed_hex` (24 hex)
- `expires_at` (decimal epoch seconds), `modulus_M`
- `storage_path`: the absolute server path. This is leaked to clients; treat
  it as informational only.

Errors: 404 `download not found` / `download preview not found`, 429
`{"ok":false,"queued":true,"error":"too many concurrent downloads","retry_after":3}`,
503 `client disconnected`.

#### Chunk GET

`/file/download/:id/chunk/:n?session_id=..&session_token=..[&span=N][&chunk_rtt_ms=..]`

`span` (default 1, clamped to 1..64, to `chunk_count - n`, and to a 128 MiB
response cap) coalesces chunks `[n, n+span)` into one contiguous response.

Response headers: `X-TASFA-Chunk-Index`, `X-TASFA-Chunk-Count`,
`X-TASFA-Chunk-Span`, `X-TASFA-Stream-Mode`, plus `X-TASFA-Content-Encoding`
and `X-TASFA-Uncompressed-Length` when compressed, `X-TASFA-Hash-Tag` /
`X-TASFA-Magic-Scalar` when HTP metadata exists, and
`X-TASFA-Predicted-Remaining-Ms` once at least 3 RTT samples exist.

Errors: 400 `invalid download chunk payload` / `download chunk out of range`,
403 `download chunk rejected` (bad token), 404 `download session not found`,
410 `download session expired` (session deleted), 500 `file size consistency
check failed` (the stored file no longer matches `total_size`), 503
`client disconnected`.

#### Complete

POST form body `session_id` + `session_token`. Success `{"ok":true}`;
increments the file's download counter and deletes the session.

### Upload

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/file/upload/init` | logged-in user | create upload session |
| POST | `/file/upload` | upload token (headers) | upload one chunk |
| POST | `/file/upload/status` | upload token | resume / progress poll |
| POST | `/file/upload/renegotiate` | upload token | recompute parallel window |
| POST | `/file/upload/complete` | upload token | finalize |
| POST | `/file/upload/cancel` | login + owner | delete sessions |

#### Init

Form fields: `filename` (required; only `/` and `\` are rejected), `total_size`
(required, > 0, capped by `max_upload_size`), `chunk_size` (hint),
`chunk_count` (ignored, recomputed), `post_id` (integer, 0 allowed),
`session_id` (stored verbatim, unused), `fec` (`"rs2"` for RS(6+2), anything
else for xor1), and the seven `link_*` telemetry fields.

Success 200: the full status JSON (below) plus `upload_id` (32 hex).

Errors: 400 `invalid upload init payload`, 400 `upload too large`,
429 `{"ok":false,"queued":true,"error":"Wait a second...","retry_after":5}`
(with a `Retry-After: 5` header), 500 `upload init failed`.

#### Chunk upload

POST `/file/upload` with a binary body of exactly one chunk and headers:

- `X-TASFA-Upload-ID`, `X-TASFA-Upload-Token`, `X-TASFA-Chunk-Index` (required)
- `X-TASFA-Stream-Mode: aes-256-gcm` when the body is encrypted
- `X-TASFA-Content-Encoding: zstd|br|gzip` when the body is compressed
  (substring-matched and case-insensitive, so `x-gzip` also matches)
- `X-TASFA-Hash-Tag`, `X-TASFA-Magic-Scalar`, `X-TASFA-Raw-Scalar` (HTP)
- `X-TASFA-Chunk-RTT` (optional RTT sample)

Success is **204 No Content** with `X-TASFA-Accepted: 1` and
`X-TASFA-Chunk-Complete: 1`, not 200 JSON. Re-sending an already-received
chunk returns the same 204 idempotently. Size validation: plain bodies must
match the expected size exactly; encrypted bodies expected size + 16 bytes of
tag; compressed bodies may be any size up to the cap. Parity chunks always
have expected size equal to the full `chunk_size`.

#### Status

POST form fields `upload_id`, `upload_token`. Success 200 status JSON:

`ok`, `upload_id`, `upload_token`, `upload_secret`, `stream_key_hex`,
`stream_iv_seed_hex`, `stream_mode`, `chunk_size`, `chunk_count` (data +
parity), `fec_mode`, `total_size`, `received_bitmap` (string of `'0'`/`'1'`
per chunk), `received_chunks`, `current_parallel_chunks`,
`initial_parallel_chunks`, `max_parallel_chunks`, `dispatch_pacing_ms`,
`modulus_M`, `group_count`, `expires_at`, `missing_vertices` (array of
`{group_index, vertex_index, chunk_index}`), optional `retry_targets`,
`suspicion_scores`, `contraction_level`, `htp_status`, `previews`
(`pending`/`done`/`failed`/`skipped`), `percent`, `predicted_remaining_ms`.

Anyone holding `upload_token` gets the session keys back from `status`.
`upload_secret` is issued but never verified by the server.

#### Renegotiate

POST form fields `upload_id`, `upload_token`, the seven `link_*` fields, and
`suggested_parallel`. Recomputes the upload window; hysteresis: the server
never drops `current_parallel_chunks` below 90% of its previous value per
call. Returns the full status JSON.

#### Complete

POST form fields `upload_id`, `upload_token`, optional `async_finalize=1`.

Completion is asynchronous: the first call schedules finalize and returns
**202** `{"ok":false,"processing":true,"status":"finalizing","retry_after":1}`;
re-POST the same request to poll until it returns 200. While processing, the
body still says `ok:false`; key on the HTTP status, not `ok`.

Errors: 400 `invalid completion payload`, 403 `upload completion rejected`,
404 `upload session not found`, 409 with status JSON and
`error: "missing upload chunks"` when any chunk (including parity) is absent,
409 with `htp_status:"needs_retry"` + `retry_targets` + `suspicion_scores` on
integrity failure, 503 `finalize queue full` / `finalize executor unavailable`.

Finalize performs FEC recovery of missing data chunks, the HTP line-sum and
permutation checks, renames the assembled file to
`public/uploads/<upload_id>_<filename>`, computes SHA-256, inserts the DB row
(`db_file_create_volume_get_id` with the client-supplied `post_id` and the
session owner's uid), then generates thumbnails/previews via ffmpeg (GIF
uploads are transparently transcoded to WebM; check `is_gif_converted`) and
optionally mirrors to S3.

Success 200 JSON: `ok`, `id`/`fid`, `filename`, `url` (`/file/download/<fid>`),
`blob_url`, `file_path`, `delete_pin` (12 hex, shown once; stored hashed),
`checksum` (64 hex SHA-256), `is_gif_converted`, and with
`async_finalize=1` also `state:"stored"` and `previews:"pending"`. Poll
`/file/upload/status` until `previews` leaves `pending`; after that the
session directory is deleted and status starts returning 404.

#### Cancel

Login required. Form field `upload_ids` is a **JSON array serialized as a
string** inside the form body (e.g. `upload_ids=["abc..","def.."]`). Sessions
owned by other users are silently skipped. Always returns `{"ok":true}`.

## Sessions

- IDs and tokens are raw CSPRNG hex (`RAND_bytes`): ids are 16 bytes (32 hex),
  tokens 24 bytes (48 hex). Tokens are compared with constant-time memcmp.
- TTL: 86400 s for both upload and download sessions. Expired download
  sessions are deleted on the next chunk request (410). Upload expiry is
  enforced by a background sweeper: a session is removed once `expires_at`
  has passed and no file in its directory changed for 3600 s.
- Sessions are multi-request and survive server restarts (state on disk).
  `complete`/`cancel` destroy them.
- Upload session directory `data/tasfa/uploads/<upload_id>/` contains:
  `meta.json`, `state.json`, `meta.bin`, `state.bin` (one `'0'`/`'1'` byte per
  chunk, updated with a locked atomic read-modify-write),
  `upload.bin.part` (preallocated to `total_size` via `ftruncate`),
  `htp.bin` (145 bytes per chunk: 129-byte hash tag slot + raw scalar +
  balanced scalar), `parity_<k>.bin`, `session.lock` (flock).
  Download sessions keep `meta.json` under `data/tasfa/downloads/`.
- In-memory: two 512-slot admission queues (swept after 600 s idle for
  uploads, 300 s for downloads), a 512-slot meta cache, a 128-slot / 1 h
  finalize idempotency cache, and a rolling 256-slot SHA-256 registry used
  only to skip re-hashing on restart-free finalize.

## Encryption wire format

- Algorithm: AES-256-GCM (OpenSSL EVP on the server, WebCrypto in the
  browser). The mode string is `"aes-256-gcm"` everywhere.
- Key: 32 random bytes, hex-delivered as `stream_key_hex`. IV seed: 12 random
  bytes as `stream_iv_seed_hex`.
- IV derivation: copy the 12-byte seed, XOR the chunk index **big-endian**
  into bytes 8..11.
- AAD: the ASCII string `"<session_id>:<chunk_index>"` (uploads use the
  upload id).
- Tag: 16 bytes, appended after the ciphertext (`ciphertext || tag`).
- **Span quirk**: a multi-chunk download span is encrypted as one GCM message
  keyed with the *first* chunk's index. Clients must decrypt a span with the
  first chunk's index, not per chunk.
- The optional WASM backend (`TASFA_CRYPTO_WASM=<module.wasm>`, override the
  runtime with `TASFA_WASMTIME`) runs one framed request per wasmtime process
  over stdin/stdout; the framing is defined in `wasm/tasfa_crypto_protocol.h`
  and is byte-compatible with the native path.

## Chunk geometry

- Upload: default 9 MiB desktop / 8 MiB mobile, min 2 MiB, same values as max
  (cwist caps request bodies at 10 MiB). The client hint is floor-rounded to a
  128 KiB quantum, then doubled up to the minimum or halved down from the
  maximum, so non-power-of-two requests can shift unexpectedly.
- Download: default 8 MiB desktop / 6 MiB mobile, min 2 MiB, max 32 MiB, with
  fast-link ceilings of 48 MiB and 64 MiB when telemetry reports
  `link_downlink_mbps >= 500` (and >= 900 for ultra), no save-data, a
  non-2g/3g effective type, and RTT <= 80 ms. Files over 100 MiB raise the
  fallback to 10/16 MiB (mobile/desktop); over 1 GiB to 14/32 MiB.
- Mobile detection is a User-Agent substring check.
- Download `span` coalescing is described under Chunk GET. Uploads have no
  span: one chunk per POST.

## FEC

Uploads split into groups of 6 data chunks.

- `xor1` (default): one parity chunk per group, the bytewise XOR of the
  group's data chunks, at index `data_chunks + g`.
- `rs2`: two parity chunks per group at indexes `data_chunks + 2g` and
  `data_chunks + 2g + 1`, computed over GF(2^8) with polynomial `0x11d`:
  P0 = sum(a_i * d_i), P1 = sum(a_i^2 * d_i) with a_i = position in group + 1.

`chunk_count` in the status JSON **includes parity chunks**. Parity chunks are
uploaded like data chunks at full `chunk_size` even for a short tail group.
Finalize recovers missing data chunks (XOR for a single erasure, a 2x2 GF
solve for a double). Recovery only fixes missing *data* chunks, and complete
requires `received == chunk_count`, so in practice **all parity chunks must be
uploaded** even when every data chunk arrived.

## HTP integrity layer

Uploads carry a second integrity scheme on top of GCM:

- `X-TASFA-Hash-Tag`: up to 128 characters, stored verbatim in the 129-byte
  per-chunk slot. Server-generated media metadata uses a 64-hex SHA-256.
- `X-TASFA-Raw-Scalar` / `X-TASFA-Magic-Scalar`: per-chunk scalars mod
  `modulus_M`. `modulus_M` is random per upload (53-bit mask); pre-computed
  media metadata uses the stable prime 4294967291.
- At finalize the server recomputes line sums per 6-chunk group
  (L1=(v0+v1+v2)%M, L2=(v2+v3+v4)%M, L3=(v4+v5+v0)%M) and runs
  swap-repair permutations, peeling XOR recovery, and contraction. Suspect
  chunks produce 409 `needs_retry` with `retry_targets` and
  `suspicion_scores`; on a legacy line-sum mismatch the whole group's bitmap
  is reset to `'0'` and the client must re-send those chunks.

## Compression

Server downloads honor `X-TASFA-Accept-Encoding` (falling back to the standard
`Accept-Encoding`) and try exactly one codec, in the preference order zstd
level 1, brotli quality 1, gzip Z_BEST_SPEED, compressing the whole payload
once and accepting only when savings strictly exceed 1024 bytes
(`X-TASFA-Content-Encoding` + `X-TASFA-Uncompressed-Length` on the response).
Compression happens before encryption; upload bodies are decompressed after
decryption. The full policy and benchmark methodology are in
[tasfa-compression.md](tasfa-compression.md). Browser clients probe
`DecompressionStream` for `br`, `zstd`, `gzip` support before advertising.

## Client download flow

`public/js/tasfa-download.js`:

1. Resolve a base URL from `data-tasfa-src`, `data-tasfa-download`, or `src`,
   and map it to a handshake URL (`/file/download/<id>/handshake`,
   `/file/preview/<id>/handshake`, or `/assets/tasfa/uploads/<name>/handshake`).
2. GET the handshake with chunk-size and link telemetry. Network errors retry
   up to 10 times with exponential backoff plus jitter (cap 16 s); 429 retries
   up to 12 times honoring `retry_after`; 5xx retries up to 10 times.
3. Register the session with the service worker via
   `postMessage({type:"TASFA_SESSION", url, sessionId, sessionToken, ultraFastConnection})`.
4. Files up to 100 MiB check the `tasfa-small-files-v1` Cache API store keyed
   by base URL first.
5. Fetch chunks with XHR (`X-Requested-With: XMLHttpRequest`,
   `X-TASFA-Accept-Encoding: <probed codecs>`), decrypt (IV seed XOR be32
   chunk index, AAD `"<session_id>:<index>"`, 128-bit tag), decompress via
   `DecompressionStream`, and verify the exact span length.
6. `max_parallel_chunks` workers claim spans of `coalesce_chunks` width;
   adaptive AIMD tuning doubles the chunk size after 6 fast successes and
   halves it on failure (persisted per client, see below). Per-chunk retries
   go up to 200 with 5 s * 2^n backoff capped at 60 s.
7. Up to 5 recovery sweeps re-fetch missing chunks with span=1; the blob is
   assembled and its size checked against `total_size`.
8. Completion is best-effort POST `/file/download/complete`.
9. Playback URLs: when the Cache API and a controlled SW are available, the
   blob is stored in `tasfa-media-cache-v2` under
   `/__tasfa_media__/<sanitized url>-<timestamp>`; otherwise a `blob:` URL is
   used (video/audio prefer the SW path because blob URLs misbehave with the
   TASFA fetch path).
10. Fallback ladder: per-chunk 400/403/404/410 or 10 combined failures ->
    plain XHR GET of `/file/download/<id>?tasfa_fallback=1` (no fallback
    exists for `/file/preview/`). Firefox XHR errors retry once per attempt
    with a `_ffcb=<timestamp>` cache-bust parameter.

## Client upload flow

`public/js/editor.js` (editor uploads; files larger than 4 MiB go through
TASFA when `use_tasfa` is on, smaller files use `POST /api/upload`):

1. `POST /file/upload/init` with filename, total_size, chunk geometry,
   `post_id`, `fec=rs2`, and link telemetry. 429 honors `retry_after` with up
   to 30 retries.
2. Chunks are POSTed round-robin across 6-chunk groups with parity last, each
   with the HTP headers (SHA-512-based per-group scalars mod `modulus_M`).
   200/204 is success; 429 retries with `retry_after` up to 40 times.
3. Adaptive chunk size is persisted in localStorage; the window follows
   `current_parallel_chunks` / `dispatch_pacing_ms` from status and
   renegotiate responses.
4. Resume: `POST /file/upload/status` returns `received_bitmap`; zero bytes
   are the resend set. Sessions survive page reloads because state lives on
   the server disk.
5. After 24 chunk failures, 40 busy retries, or a predicted fallback, chunks
   are sent encrypted (gzip via `CompressionStream` when > 1024 bytes, then
   AES-256-GCM with the upload stream key, same IV/AAD scheme, plus
   `X-TASFA-Stream-Mode` / `X-TASFA-Content-Encoding` headers).
6. `complete` with `async_finalize=1`; 202 responses are polled, 409
   `retry_targets` triggers resend (up to 20 rounds), then previews are
   polled until `previews` leaves `pending`.
7. Renegotiate posts new telemetry and `suggested_parallel` when link quality
   changes.

## Service worker contract

`public/sw.js`:

- **Bypassed** (never intercepted): cross-origin requests; non-GET; any URL
  containing `/login`, `/register`, `/logout`, `/comment/`, `/account/`,
  `/chunk/`, `/handshake`, `/file/upload`, `tasfa_fallback=1`, or
  `session_id=`.
- **`/file/download/` GETs**: waits up to 2 s (50 ms poll) for a registered
  `TASFA_SESSION`, then injects `X-TASFA-Session-ID` / `X-TASFA-Session-Token`
  headers so plain `<video src="/file/download/N">` streaming works. Range
  requests pass through real 206 responses (or untouched on ultra-fast links);
  otherwise the SW synthesizes 206 (suffix ranges and 416 supported,
  multi-range answered with 200).
- **`/__tasfa_media__/` GETs**: served from the `tasfa-media-cache-v2` cache,
  network on miss, Range-aware via synthesized 206.
- **`/__tasfa_stream__/<id>`**: progressive video streaming. The client opens
  a stream with a `TASFA_STREAM_OPEN` MessageChannel message and feeds chunks
  in order with transferable `TASFA_STREAM_CHUNK` messages;
  `TASFA_STREAM_CLOSE` releases the entry after a 60 s grace period.
- Cache namespaces: `fly-precache-v11` (app shell; deliberately excludes
  tasfa-download.js), `fly-static-v9` (7 d static), `fly-cdn-v3` (30 d CDN),
  `logo-cache-v6` (1 h), `tasfa-media-cache-v2`, `tasfa-small-files-v1`.
  Activation deletes every cache not in this list and any cache whose name
  contains `navigation`.
- Navigations get a per-client `Authorization: Bearer` token (12 h TTL) synced
  through `AUTH_TOKEN` messages, plus fetch-with-retry.

| Attribute | Element | Meaning |
|---|---|---|
| `data-tasfa-src` | img/video/audio | explicit TASFA base URL (checked before `src`) |
| `data-tasfa-download` | media | TASFA base URL; also written back by the upgrader |
| `data-tasfa-download-link` | a | click starts a chunked download |
| `data-tasfa-video-link` | button | hover/focus/touch pre-warms the session; click opens the video modal |
| `data-tasfa-poster` | media | poster override; ignored unless it is a TASFA URL |
| `data-tasfa-original` | img | original file URL for the overlay Download button |

| `data-tasfa-fixed-preview="1"` | img | skip adaptive `w=`/`h=` resize parameters |
| `data-tasfa-animation-url` | img | Range-probed; if it answers `video/*`, the img is swapped for a looping muted video |
| `data-tasfa-skip="1"` | media | opt out of the upgrader |

Client-written state attributes: `data-tasfa-ready`, `data-tasfa-progress`,
`data-tasfa-error`, `data-tasfa-media-bound`, `data-tasfa-video-bound`,
`data-tasfa-animation-bound`, `data-tasfa-download-bound`.

Images without `data-tasfa-fixed-preview` get DPR-aware `?w=&h=` parameters:
display size times DPR (max 2), rounded up to 128, clamped 256-1920.

## Client adaptive state (localStorage)

- `tasfa_download_chunk_size_v3`: download chunk size, clamped 2-32 MiB in
  512 KiB steps, default 8 MiB desktop / 4 MiB mobile. Doubled after 6 fast
  successes, halved on failure.
- `tasfa_upload_chunk_size_v3`: upload chunk size, 8-64 MiB (32 MiB cap on
  mobile), default 32 MiB desktop / 12 MiB mobile.

## Rate limiting and error codes

- Upload init queue full: 429 `{"ok":false,"queued":true,"retry_after":5}`
  with `Retry-After: 5`.
- Handshake queue full: 429 `too many concurrent downloads`, `retry_after: 3`.
- Finalize table full: 503 `finalize queue full`.
- Global async defer queue full: 503 with `Retry-After: 5` and a plain-text
  overload message.
- Handlers probe the client socket (`recv MSG_PEEK`) and abort dead
  connections early: 503 `client disconnected` on handshake/chunk, 400 at
  finalize.
- Expired download session: 410 `download session expired`.

| Key | Default | Meaning |

## Quirks a client implementer must know

- Chunk upload success is **204 with no body**, not 200 JSON.
- `complete` is asynchronous; the first call answers 202 and polling means
  re-POSTing the same request. Cached progress bodies still say `ok:false`.
- Upload `chunk_count` includes parity chunks, and finalize requires all of
  them; parity is for server-side recovery of *data* chunks only.
- A spanned download is one GCM message keyed by the first chunk's index.
- Savings must strictly exceed 1024 bytes or the response is sent raw;
  exactly 1024 bytes saved is not enough.
- The client `already_done` fast path in editor.js has no server counterpart;
  no C code ever emits it.
- GIF uploads are transcoded to WebM server-side; `filename` and `total_size`
  change, and `is_gif_converted` is set.
- Filenames reject only `/` and `\`; final files are stored as
  `public/uploads/<upload_id>_<filename>`, which neutralizes traversal.
- Cancel takes a JSON-array-as-string form field and silently ignores
  sessions owned by other users.
- Renegotiate refuses to shrink the parallel window below 90% of its previous
  value per call.
- The upload `session_id` field is stored but never used by the server.
- `upload_secret` is issued but never verified; `status` returns the session
  keys to anyone holding `upload_token`, and the download handshake leaks
  `storage_path`. None of these cross a trust boundary that TLS does not
  already define, but do not treat them as secrets.
