# TASFA

TASFA — это протокол передачи файлов, используемый в данном проекте для загрузки и скачивания.

Он построен поверх обычного HTTP/XHR и добавляет шифрование по частям, последовательную очередь на уровне файла, а также **серверную решётку восстановления HTP (Hexagonal Tortoise Problem) с 6 слотами** для контроля целостности.

## Маршруты

Загрузка:
- `POST /file/upload/init`
- `POST /file/upload/status`
- `POST /file/upload/renegotiate`
- `POST /file/upload`
- `POST /file/upload/complete`
- `POST /file/upload/cancel`

Скачивание:
- `GET /file/download/:id/handshake`
- `GET /file/download/:id/chunk/:chunk_index`
- `GET /file/download/:id`
- `GET /assets/tasfa/img/:filename/handshake`
- `GET /assets/tasfa/img/:filename/chunk/:chunk_index`
- `GET /assets/tasfa/uploads/:filename/handshake`
- `GET /assets/tasfa/uploads/:filename/chunk/:chunk_index`

## Протокол Загрузки

Браузер сначала согласовывает сессию загрузки, затем отправляет **чанки** (по умолчанию `16 MiB`, на мобильных `8 MiB`) с заголовками TASFA:

- `X-TASFA-Upload-ID`
- `X-TASFA-Upload-Token`
- `X-TASFA-Chunk-Index`
- `X-TASFA-Hash-Tag`
- `X-TASFA-Raw-Scalar`
- `X-TASFA-Magic-Scalar`

Сервер записывает каждый чанк непосредственно в предварительно выделенный временный файл по смещению `chunk_index * chunk_size`. Транспортных блоков больше нет.

Если обычный чанк многократно завершается с ошибкой, браузер отправляет этот неудавшийся чанк через запрос отката AES-256-GCM с `X-TASFA-Stream-Mode: aes-256-gcm`. Сервер принимает шифротекст вместе с тегом аутентификации GCM, и чанки отката остаются внутри адаптивного параллельного окна. Запрос отката по-прежнему содержит те же заголовки хеш-тега HTP и сбалансированного скаляра.

### XOR-чанки чётности

Сессии загрузки содержат один дополнительный **чанк чётности на группу из не более чем 6 чанков данных**: `chunk_count = data_chunks + ceil(data_chunks / 6)`. Чанк чётности хранит `P = C_0 xor ... xor C_n` для своей группы и сохраняется отдельно как `parity_<k>.bin` в каталоге сессии вместо смещения `chunk_index * chunk_size`. Чанки чётности учитываются в битовой карте полученных чанков, но исключаются из валидации линий HTP; они питают серверное пилинг-восстановление, описанное ниже.

### Остаток (последний частичный чанк)

Если размер файла не кратен размеру чанка, последний чанк является **остатком**. Он отправляется как единый blob с точным диапазоном байтов; сервер записывает его по правильному смещению. Заполнение или разделение не выполняется.

### Ответ инициализации сессии

Конечная точка `init` возвращает, среди прочего:

- `chunk_size` — согласованный размер чанка
- `current_parallel_chunks` — одобренное сервером текущее окно загрузки
- `max_parallel_chunks` — сколько чанков клиент может загружать параллельно
- `dispatch_pacing_ms` — небольшая задержка отправки, применяемая только при плохом измеренном канале
- `upload_secret` — дополнительный серверный секрет для проверки зашифрованного потока
- `stream_key_hex`, `stream_iv_seed_hex`, `stream_mode` — ключи шифрования сессии (`aes-256-gcm`)
- `modulus_M` — модуль HTP, используемый для этой сессии
- `group_count` — количество полных 6-слотовых HTP-групп
- `client_stripes` — фиксированное значение `32`, используемое планировщиком рабочих потоков клиента

Клиент рассматривает `chunk_size` как контракт сессии, поскольку он определяет смещение каждого чанка в файле. Во время активной загрузки он настраивает параллелизм и поведение повторных попыток, а изученная подсказка размера чанка применяется к следующей сессии TASFA: после устойчивой быстрой серии (3 чистых чанка при EWMA `>= 8 Mbps` или времени чанка менее 30 секунд) следующая подсказка удваивается, а после неудач снижается на четверть (`* 0.75`, округление до шагов `1 MiB`, нижняя граница `8 MiB`).

### Ответ на загрузку чанка

Когда чанк принят, сервер отвечает `204 No Content` и заголовками:

- `X-TASFA-Accepted: 1`
- `X-TASFA-Chunk-Complete: 1`

Если индекс чанка уже помечен как завершённый в `state.bin` **и** этот индекс отсутствует в списке `retry_targets` сервера, сервер возвращает `204` с теми же заголовками, но тело чанка отбрасывается.

## Серверная Решётка Восстановления HTP

HTP **не является транспортным протоколом и не является криптографическим доказательством**. Это серверный движок подозрения в отношении чанков, который ранжирует чанки по вероятности повреждения, чтобы клиент повторно передавал только высоковероятных подозреваемых вместо всего файла.

### Группировка чанков

Чанки группируются в последовательные вершины из 6 элементов:

```
Группа g: [ v0 , v1 , v2 , v3 , v4 , v5 ]
            chunk g*6+0  ...  g*6+5
```

Последняя группа может быть неполной; **неполные группы никогда не заполняются нулями и полностью исключаются из валидации HTP**. Заполнение нулями внедряло бы синтетическую топологию и запрещено.

### Исходный скаляр

Для каждого чанка клиент вычисляет SHA-512 открытого текста чанка, берёт первые 8 байтов как беззнаковое 64-битное целое число big-endian `H` и выводит:

```
raw_scalar = H % modulus_M
```

### Инвариант магической линии

Для полной группы определяются три линии:

```
L1 = v0 + v1 + v2   (mod M)
L2 = v2 + v3 + v4   (mod M)
L3 = v4 + v5 + v0   (mod M)
```

Инвариант требует `L1 == L2 == L3`. Если исходные скаляры не удовлетворяют этому, клиент **балансирует**, корректируя только `v3` и `v5`:

```
delta2 = (L1 - L2) mod M
delta3 = (L1 - L3) mod M

v3_balanced = (v3_raw + delta2) mod M
v5_balanced = (v5_raw + delta3) mod M
```

Все остальные вершины сохраняют свой исходный скаляр. Клиент отправляет оба:

- `X-TASFA-Raw-Scalar` — немодифицированный `raw_scalar`
- `X-TASFA-Magic-Scalar` — сбалансированное значение (`v3_balanced` или `v5_balanced`, в остальных случаях совпадает с raw)

Сервер хранит оба скаляра отдельно в `htp.bin`, чтобы анализ мог ссылаться на исходную топологию независимо от искусственных ограничений балансировки.

### Почему только v3 и v5?

Шестиугольная решётка имеет две степени свободы. Фиксируя `v0,v1,v2,v4` и корректируя `v3,v5`, можно единственным образом удовлетворить трём уравнениям линий, сохраняя минимальную дельту и локальность внутри группы.

## Серверное Восстановление HTP

**Клиент — это тупой агент повторной передачи.** Он не вычисляет алгебру восстановления, не оценивает пороги стоимости и не выводит ранжирование подозреваемых. Всё это находится исключительно на сервере.

### Поток валидации сервера

Во время `POST /file/upload/complete` сервер:

1. Загружает все записи для каждого чанка из `htp.bin` (хеш-тег, raw-скаляр и сбалансированный скаляр).
2. Проверяет только **полные группы из 6 слотов** (частичные группы пропускаются).
3. Если порядок скаляров внутри группы из 6 слотов переставлен (вне порядка), сервер перебирает все 720 перестановок, находит ту, которая восстанавливает инвариант, и перестраивает записи `htp.bin` соответственно без повторной передачи.
4. Для каждой неудавшейся группы вычисляет **оценки подозрения** для каждого слота, анализируя участие в уравнениях линий.

### Оценка достоверности подозрения (по группам)

Для неудавшейся группы сервер оценивает каждый слот по отношению к трём уравнениям линий:

| Слот | Уравнения |
|------|-----------|
| v0   | L1, L3    |
| v1   | L1        |
| v2   | L1, L2    |
| v3   | L2        |
| v4   | L2, L3    |
| v5   | L3        |

Подозрительный балл каждого слота выводится из топологического синдромного анализа:
- Когда совпадают ровно две линии, а одна отличается ($L_a == L_b \neq L_c$), ошибочное уравнение выделяет двух кандидатов: слот-эксклюзив на стороне $L_c$ (балл `1.0`, доминирующий синдром) и противоположный угловой слот, общий для $L_a, L_b$ (балл `0.5`).
- Оставшиеся 4 слота, не затрагиваемые ошибочным уравнением, немедленно **очищаются** (балл `0.0`).
- Когда все три линии различаются ($L_1 \neq L_2 \neq L_3$), баллы пропорциональны участию в нормализованных величинах остатков $|L_i - L_j|$.

Оценки агрегируются по всем неудавшимся группам; если чанк появляется в нескольких группах, сохраняется максимальная оценка.

### Полный XOR-Пилинг-Декодер HTP

Чтобы устранить повреждение или потерю чанков без дорогих обращений матриц в поле Галуа $GF(2^8)$, TASFA сочетает топологическую синдромную локализацию с итеративным пилинг-декодером XOR:
- **Генерация XOR-чётности**: Каждая группа из не более чем 6 чанков данных имеет чанк чётности $P = C_0 \oplus C_1 \oplus C_2 \oplus C_3 \oplus C_4 \oplus C_5$, загружаемый вместе с сессией.
- **Локализация подозреваемого с нулевой стоимостью**: Когда группа не проходит проверки целостности, суммы линий HTP точно указывают индекс единственного повреждённого чанка $i$ за $O(1)$ целочисленных операций.
- **Ограниченное итеративное пилинг-восстановление**: Сервер восстанавливает $C_i = P \oplus \bigoplus_{j \neq i} C_j$, используя побитовый XOR с SIMD-оптимизацией. Группа восстанавливается, когда у неё ровно один подозреваемый, или два подозреваемых, где верхний балл равен `1.0` (доминирующий синдром одиночной ошибки); все подозреваемые восстановленной группы затем очищаются. Сканирование повторяется, пока группы продолжают продвигаться, максимум за 6 проходов.
- **Восстановление отсутствующего чанка**: Независимо от анализа подозрения, если битовая карта завершения показывает ровно один отсутствующий чанк данных в группе и чанк чётности этой группы получен, сервер восстанавливает отсутствующий чанк тем же способом перед валидацией линий HTP.
- **Резервный вариант при множественных стираниях**: Если два или более независимых чанка в одной группе не могут быть изолированы, сервер откатывается к ARQ-повторной передаче через `retry_targets`.

### Порог стоимости восстановления

Перед запросом любого восстановления сервер оценивает, дешевле ли сжатие, чем прямая повторная передача:

```
repair_worthwhile(подозреваемые, всего, размер_чанка, rtt_ms):
    if подозреваемые < 12               → false  (слишком мало для топологии)
    retry_cost  = подозреваемые * размер_чанка * rtt_factor(rtt_ms)
    repair_cost = метаданные_байты + cpu_сервера + доп_rtt_стоимость
    return retry_cost > repair_cost
```

Абстрактная модель затрат сравнивает байты, которые клиент должен повторно передать, с накладными расходами на анализ на стороне сервера. Большие чанки или высокая задержка делают сжатие более привлекательным, а множество мелких подозреваемых — прямой повтор дешевле. Конкретные числа являются деталями реализации сервера, а не константами протокола.

Если порог отклоняет восстановление, сервер возвращает `needs_retry` со **всеми** подозреваемыми чанками в качестве целей повторной передачи. Клиент повторно передаёт их через обычную конечную точку загрузки.

### Серверное рекурсивное сжатие

Если восстановление целесообразно, сервер выполняет **сжатие на уровне групп**: каждая оригинальная полная 6-слотовая группа сворачивается в один скаляр, кодирующий её **сигнатуру инварианта**. Сервер вычисляет три значения линии `L1, L2, L3` группы, выводит остатки `r12 = (L1-L2) mod M` и `r23 = (L2-L3) mod M`, и устанавливает групповой агрегат равным `(r12 * r23) mod M`. Проходящая группа имеет `r12 = r23 = 0`, поэтому её агрегат равен `0`; неудавшаяся группа получает ненулевую детерминированную сигнатуру, сохраняющую топологию несоответствий линий. Эти групповые агрегаты становятся вершинами решётки HTP более высокого уровня. Последовательные группы по 6 таких агрегатов формируют супер-группы уровня 1, и те же линейные инварианты переоцениваются:

- Если супер-группа уровня 1 проходит, подозреваемые из её базовых групп уровня 0 очищаются (паттерн отказа согласован на уровне групп).
- Если супер-группа уровня 1 не проходит, подозреваемые из её базовых групп уровня 0 сохраняются.
- Если сжатие сужает множество подозреваемых (меньше чанков), сервер сохраняет суженные цели и возвращает `needs_retry` с уменьшенным списком.
- Если сжатие не сужает множество, сервер откатывается к прямой повторной передаче исходных подозреваемых.
- Уровень сжатия инкрементируется в метаданных сессии, чтобы клиент мог сообщать диагностику.

Клиент никогда не видит группы сжатия и не вычисляет их. Он получает только `retry_targets`.

### Принятие повторной передачи

Когда клиент повторно передаёт чанк, уже помеченный как полученный, обычная конечная точка загрузки **принимает повторную передачу только если индекс этого чанка в данный момент находится в списке `retry_targets` сервера**. После сохранения повторно переданного чанка сервер удаляет его из `retry_targets`.

### Видимый протоколу ответ восстановления

При сбое HTP, когда сервер принимает решение о восстановлении или повторной передаче, конечная точка `complete` возвращает `409` с:

- `htp_status`: `"needs_retry"`
- `retry_targets`: массив индексов чанков для повторной передачи (упорядочен по убыванию оценки подозрения)
- `suspicion_scores`: массив объектов `{chunk_index, score}`
- `contraction_level`: сколько проходов серверного сжатия было применено
- `retry_reason`: читаемое человеком объяснение (например, `"htp group inconsistency detected"`)

Если порог стоимости говорит, что прямая повторная передача дешевле, `retry_targets` содержит полный список подозреваемых, а `contraction_level` остаётся `0`.

Если сервер успешно сужает подозреваемых через сжатие, `retry_targets` содержит суженный список, а `contraction_level` увеличивается.

После того как все подозреваемые чанки повторно переданы и успешно проверены, следующий вызов `complete` переходит к финализации SHA-256.

## Последовательная Очередь на Уровне Файла

**Одновременно загружается только один файл.** При выборе нескольких файлов:

1. Каждый файл получает свой собственный ресурс, карточку предпросмотра и сессию HTP.
2. Файлы ставятся в очередь `FileUploadQueue`.
3. Когда активный файл завершается (успех или неудача), очередь автоматически переходит к следующему файлу.
4. Кнопка пакетной загрузки «Загрузить файлы в очереди» всегда активна; при нажатии она ставит в очередь все ожидающие файлы и запускает насос.

Это предотвращает исчерпание пула соединений браузера и поддерживает надёжное обнаружение зависаний.

## Настройки Времени Выполнения

- размер чанка загрузки: `16 MiB` на десктопе, `8 MiB` на мобильных
- адаптивная подсказка размера чанка загрузки: минимум `8 MiB`, максимум `32 MiB` на десктопе / `16 MiB` на мобильных при серверном согласовании (предпочтение клиента может достигать `64 MiB` / `32 MiB`); успех удваивает подсказку после быстрой серии, неудача снижает её на `* 0.75` шагами по `1 MiB`
- размер чанка скачивания: `8 MiB` на десктопе, `6 MiB` на мобильных, до `32 MiB` когда клиент указывает большую сессию
- параллелизм загрузки браузера по умолчанию: `8`, успех `*1.15` (`*1.3` в окне быстрого восстановления), неудача `*0.85`
- максимальный параллелизм загрузки браузера: `max_upload_parallel_chunks` в `blog.settings`, ограничение `40`
- максимальное количество параллельных сессий загрузки: `max_total_parallel_uploads` в `blog.settings`, ограничение `512`
- максимальный размер загрузки: `max_upload_size` в `blog.settings`
- максимальное количество сессий скачивания браузера: определяется сервером, до `48` запросов чанков на сессию
- объединение при скачивании (размер группы span): успех `*1.2`, неудача `*0.8`; серверный профиль подсказывает до `16` чанков, а клиентский span может вырасти до `64` чанков с ограничением `128 MiB` на запрос
- предпросмотры изображений: запрос размера с учётом DPR, корзина 128px (минимум `256px`, максимум `1920px`), чтобы передача изображений не раздувалась до десктопного размера предпросмотра, когда оно отображается маленьким
- воспроизведение видео/аудио: предварительный прогрев только рукопожатия сессии TASFA по намерению указателя/фокуса, затем сохраняется нативное воспроизведение с range-запросами; медиа-полезная нагрузка не загружается заранее, а прогрессивный планировщик остаётся неизменным
- тайм-аут xhr загрузки: адаптивный сторожевой таймер простоя, масштабируемый по размеру передачи, `30–120 с`
- тайм-аут fetch сессии загрузки: `120 с`

TASFA настроен для типичных высокопропускных серверных развёртываний, а не для встраиваемого/аэрокосмического профиля с низкой пропускной способностью. Ограничение HTTP-соединений браузера на origin естественным образом соблюдается пулом воркеров.

### Адаптация Клиента

Клиент загрузки измеряет время завершения чанка, повторные попытки, таймауты и подсказки API информации о сети, когда они доступны. Он отправляет эти данные на `/file/upload/init` и `/file/upload/renegotiate`; сервер отвечает текущим параллельным окном и максимальным окном. Чистые завершения увеличивают активное окно на `*1.15` до согласованного максимума (`*1.3` внутри 5-секундного окна быстрого восстановления сразу после падения), в то время как повторяющиеся предсказуемые паттерны сбоев снижают его на `*0.85` до нижней границы `4` на мобильных / `8` на десктопе на хороших каналах. Откат AES-GCM также выполняется внутри адаптивного окна.

Абсолютный таймаут на чанк предотвращает зависания, вызванные соединениями, которые получают часть данных, но никогда не закрываются. Сторожевой таймер (watchdog) замеряет активность загрузки каждые 2 секунды: при мягком зависании (без прогресса чанка в течение `30 с`) выполняется **мягкое восстановление** — реконфигурация (renegotiation), увеличение параллелизма и 5-секундное окно быстрого восстановления — без разрыва живых соединений; при жёстком зависании (`90 с`) выполняется **агрессивный перезапуск**: выполняющиеся XHR-запросы прерываются, а загрузка возобновляется с серверного битмапа, реконфигурируясь из полного окна `maxParallel` (высокопроизводительные профили передачи также сбрасывают `targetParallel` на `maxParallel`, а `dispatchPacingMs` на `0`). Подсказка размера чанка, полученная в процессе обучения, сохраняется **локально в сессии** и не записывается немедленно в `localStorage`; она применяется только к следующей сессии TASFA.

Скачивание использует тот же высокопроизводительный уклон: рукопожатие несёт предпочтительную подсказку размера чанка клиента, и активные скачивания увеличивают `span` и параллелизм в `*1.2` раза после успешных групп чанков. При неудаче оба снижаются в `*0.8` раза. Короткие чтения, таймауты и сетевые ошибки ставятся обратно в очередь по индексу чанка; неудавшаяся группа не приводит к провалу всего скачивания, пока тот же чанк не исчерпает высокий бюджет повторных попыток.

Для прогрессивного воспроизведения видео/аудио TASFA строже: клиент собирает и подаёт чанки последовательно, а ограниченный планировщик удерживает адаптивный параллелизм только внутри прямого окна от следующего нужного плееру чанка. Неудавшиеся или превысившие таймаут чанки записывают время повторной попытки и освобождают сетевой слот, поэтому планировщик может продолжать заполнять другие допустимые чанки в том же окне. Воспроизведение может останавливаться на границе буфера, но оно никогда не пропускает диапазон байтов, не оставляет чанк нерешённым и не закрывает медиапоток раньше времени.

### Предсказание RTT Хвоста (Экстраполяция Лагранжа)

Для больших файлов (сессий с большим количеством чанков) сервер накапливает образцы RTT по чанкам, сообщаемые клиентом, максимум до 8. Как только собрано 3 или более образцов, полиномиальная экстраполяция Лагранжа оценивает RTT на индексе последнего чанка, и количество оставшихся чанков умножается для получения оценочного оставшегося времени.

- Загрузка: после завершения каждого чанка клиент может прикрепить заголовок `X-TASFA-Chunk-RTT` (миллисекунды) к следующему запросу чанка.
- Скачивание: клиент может отдельно сообщить RTT предыдущего чанка через параметр запроса `chunk_rtt_ms`.

Сервер добавляет `predicted_remaining_ms` в JSON-ответ состояния, а ответ на запрос чанка скачивания содержит заголовок `X-TASFA-Predicted-Remaining-Ms`. Математика намеренно остаётся лёгкой: ограничение в 8 образцов, простой O(n²) Лагранж, и предсказания ограничиваются потолком в 30 секунд.

### Предиктивная Защита с Ускорением Винна

TASFA не предсказывает байты открытого текста и не доверяет предсказанному содержимому чанков. Предсказание ограничено последовательностью качества передачи, наблюдаемой клиентом: время завершения, пропускная способность, повторные попытки, таймауты и короткие чтения. Клиент применяет epsilon-преобразование Винна в форме Aitken `Delta^2` к последним образцам качества:

```
S_hat = S0 - ((S1 - S0)^2 / (S2 - 2*S1 + S0))
```

`S_hat` ограничивается диапазоном `[0, 1]` и используется только как защитный сигнал для следующего чанка. Высокое предсказанное качество сохраняет обычный путь и позволяет адаптивному окну расти. Средне-низкое предсказанное качество помечает следующий чанк как `guarded`, уменьшая активное параллельное окно на один перед отправкой. Очень низкое предсказанное качество помечает следующий чанк загрузки для параллельного отката AES-GCM, или уменьшает `span` и параллелизм скачивания перед выдачей следующей группы диапазонов. Это опережающая защита от перегрузки и сбоев, а не криптографический оракул.

## Модель Хранения

Каждая сессия загрузки предварительно выделяет один временный файл:

- временный файл: `data/tasfa/uploads/<upload_id>/upload.bin.part`
- метаданные: `data/tasfa/uploads/<upload_id>/meta.json`
- быстрая бинарная мета: `data/tasfa/uploads/<upload_id>/meta.bin`
- состояние: `data/tasfa/uploads/<upload_id>/state.json`, `data/tasfa/uploads/<upload_id>/state.bin`
- HTP уровень 0: `data/tasfa/uploads/<upload_id>/htp.bin`
- блокировка сессии: `data/tasfa/uploads/<upload_id>/session.lock`

Сервер больше не поддерживает `blocks.bin` или `chunk_counts.bin`. Завершение чанка — это одна запись битовой карты.

### Опциональное S3-совместимое объектное хранилище

Завершённые файлы могут дополнительно храниться в S3-совместимом бакете, настраиваемом через необязательный файл `s3.settings` (полностью пустой означает «отключено», локальное дисковое хранилище не меняется). В режиме `mode=mirror` (по умолчанию) локальный файл сохраняется и также отправляется (PUT) в бакет; скачивание продолжает отдаваться с диска. В режиме `mode=offload` байты перемещаются в S3 после загрузки, строка файла помечается `s3://<key>`, а скачивание отвечает перенаправлением `302` на предписанный (presigned) GET URL сроком 1 час. Неудачные S3 PUT откатываются к локальному хранилищу, а все пути удаления очищают обе копии. Полный справочник ключей см. в `S3.md`.

Метаданные сессии также хранят массивы по вершинам:

- `hash_tags` — массив шестнадцатеричных строк SHA-512, по одной на чанк
- `magic_scalars` — массив сбалансированных скаляров, по одному на чанк
- `htp_retry_targets` — текущий список целей повторной передачи, выданный сервером
- `htp_suspicion_scores` — текущее ранжирование подозрения
- `htp_contraction_level` — количество применённых проходов серверного сжатия

Они обновляются при каждой загрузке чанка и проверяются при завершении.

## PIN Удаления

Завершённые загрузки получают одноразовый PIN удаления. Чистый PIN — это 12-символьная шестнадцатеричная строка (6 случайных байтов); возвращается один раз, хранится только его хеш.

## Протокол Скачивания

1. Клиент запрашивает рукопожатие через `GET /.../handshake`.
2. Сервер возвращает `session_id`, `session_token`, `chunk_size`, `chunk_count`, подсказки параллелизма и сессионные ключи шифрования (`stream_key_hex`, `stream_iv_seed_hex`).
3. Клиент получает группы чанков с адаптивным `span=...`. При наличии сессионных ключей все чанки зашифрованы с помощью **AES-256-GCM**.
4. Клиент расшифровывает чанки в браузере, используя **Web Crypto API** и ключи сессии.
5. Браузер собирает ответ в один непрерывный буфер.
6. **Сжатие полезной нагрузки (откат Zstd/Brotli/Gzip)**:
   При скачивании клиент объявляет поддерживаемые алгоритмы декомпрессии заголовком `X-TASFA-Accept-Encoding` (например, `br, zstd, gzip`; при отсутствии заголовка TASFA сервер откатывается к `Accept-Encoding`). Заголовок является списком возможностей, а не порядком приоритета: сервер применяет сжатие **до** шифрования GCM, выполняя ровно один полнобуферный проход наиболее предпочитаемого поддерживаемого кодека, в порядке **Zstd (уровень 1) → Brotli (качество 1) → gzip (best speed)**; это порядок предпочтения, а не цепочка отката — если выбранный кодек не экономит достаточно байтов, отдаётся исходная полезная нагрузка, и другой кодек не пробуется. Это избегает двойного сжатия и гарантирует, что клиенты получают полезную нагрузку, которую могут нативно декомпрессировать (с помощью `DecompressionStream`). Если сжатие не даёт достаточного выигрыша (`TASFA_COMPRESS_MIN_GAIN_BYTES`, 1,024 байта; требуется строго больший выигрыш), сервер пропускает сжатие и отдаёт исходную бинарную полезную нагрузку напрямую. Сжатые ответы на чанки содержат `X-TASFA-Content-Encoding` и `X-TASFA-Uncompressed-Length`, чтобы клиент мог декомпрессировать перед расшифровкой.

## Опциональная WASM-Песочница для Блочного Шифрования

Блочный AES-256-GCM (шифрование/расшифровка чанков) обычно выполняется через нативный путь OpenSSL EVP. Когда переменная окружения `TASFA_CRYPTO_WASM` указывает на собранный WASI-модуль (`make wasm-tasfa-crypto` производит `build-wasm/tasfa_crypto.wasm`), сервер вместо этого выполняет каждую блочную операцию внутри песочницы: он запускает `wasmtime run <module>` как дочерний процесс и обменивается одним фреймированным запросом/ответом (протокол в `wasm/tasfa_crypto_protocol.h`) через stdin/stdout. Модуль выполняет ту же деривацию IV и ту же раскладку AAD, что и нативный путь, а побайтовое равенство с OpenSSL EVP проверяется `wasm/test_parity.py`. Бэкенд строго опционален: если `TASFA_CRYPTO_WASM` не задана или модуль нечитаем, `tasfa_wasm_crypto_available()` возвращает false и используется нативный путь. Бинарник `wasmtime` можно переопределить через `TASFA_WASMTIME`. Это меняет только место выполнения криптографии чанков, но никогда — формат на проводе.

## Защита от DoS через Битовую Карту

И состояние загрузки, и состояние скачивания отслеживаются с помощью **плотной бинарной битовой карты** (1 байт на чанк, `'0'` / `'1'`).

### Сторона загрузки

- Сервер отклоняет любой чанк, индекс которого уже помечен `'1'` в `state.bin`, **если только этот чанк не находится явно в списке целей повторной передачи сервера**. Злоумышленник не может воспроизводить произвольные чанки для расходования дискового I/O.
- `state.bin` обновляется через `pwrite(..., 1, chunk_index)` — атомарная запись за O(1). На критическом пути отсутствует JSON-парсинг.
- Обработчик `complete` повторно открывает битовую карту, считает установленные биты и отказывается финализировать до тех пор, пока `received_chunks == chunk_count`. Это предотвращает атаки с усечёнными файлами.

### Укрепление сессий

- ID загрузки и токены — это случайные шестнадцатеричные строки длиной 16 и 24 байта.
- Блокировки сессий (`flock` на `session.lock`) предотвращают состязательные обновления битовой карты из параллельных запросов.

## Планировщик Рабочих Потоков

Сервер использует планировщик рабочих потоков с фиксированным циклическим перебором. Количество рабочих потоков равно числу ядер CPU (минимум 2, максимум 64). Чанки, принадлежащие одному `upload_id`, всегда направляются одному и тому же рабочему потоку для локальности кэша и упорядоченности. Задания отправляются через очередь на рабочий поток и сигнализируются с помощью условных переменных.

## Асинхронная Финализация

`POST /file/upload/complete` обрабатывается асинхронно. Первый вызов возвращает `202 Accepted` с `{"processing": true}` и планирует фонового рабочего финализации в пуле engine, в изолированном домене планирования `TTAK_TASK_DOMAIN_THREAD`, чтобы работа финализации (медиатранскодирование, контрольная сумма SHA-256, записи в базу данных) никогда не делила рабочие потоки с циклами обслуживания HTTP. Если пул отклоняет задание (например, при остановке), запись финализации помечается `503`, и клиент повторяет попытку вместо блокировки HTTP-воркера. Последующие вызовы `complete` опрашивают кэш финализации; когда рабочий поток завершается, кэшированный статус и тело немедленно возвращаются. Это предотвращает блокировку HTTP-соединения длительной финализацией.

## Контрольный Список Самопроверки

| Вопрос | Ответ |
|--------|-------|
| Q1: Вычисляет ли клиент какую-либо алгебру восстановления? | **Нет.** Клиент — это тупой агент повторной передачи. Вся деривация подозреваемых, оценка достоверности, пороги стоимости и логика сжатия являются исключительно серверными. |
| Q2: Является ли оценка порога стоимости восстановления явной перед сжатием? | **Да.** `htp_repair_worthwhile` сравнивает `retry_cost_estimate` (байты × RTT) с `repair_cost_estimate` (серверные накладные расходы анализа). Он отклоняет восстановление, когда `suspect_count < 12` или прямая повторная передача дешевле, возвращаясь к прямой повторной передаче. |
| Q3: Заполняются ли частичные группы нулями? | **Нет.** Проверяются только полные группы из 6 слотов (`data_chunks / 6`). Неполная последняя группа полностью исключается. |
| Q4: Содержит ли ответ оценки подозрения, а не только бинарные флаги? | **Да.** Каждый ответ `needs_retry` включает `suspicion_scores` как объекты `{chunk_index, score}`. |
| Q5: Сохраняет ли сжатие исходную топологию групп? | **Да.** `htp_contract_groups` обрабатывает каждую оригинальную полную группу как единую вершину высшего уровня; подозреваемые чанки никогда не перетасовываются между группами. |
| Q6: Очищаются ли цели повторной передачи при успешной повторной передаче? | **Да.** `handler_file_upload` удаляет чанк из `htp_retry_targets` после принятия повторной передачи. |
| Q7: Восстанавливает ли сервер переставленные скаляры обменом? | **Да.** `htp_try_swap_repair` перебирает все 720 перестановок группы из 6 слотов; если какая-либо восстанавливает инвариант, записи `htp.bin` немедленно перестраиваются, и группа проходит без повторной передачи. |
